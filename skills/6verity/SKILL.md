# 验证和验收（Typst / LaTeX）

本 skill 是完整工作流的最后一关。它不重新建模、不生成新结果、不代替写作阶段重写论文；它负责发现硬错误、修复可直接修复的问题，并输出 `reports/VERIFY_REPORT.md`。

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的"论文验收与一致性"小节。该文件只是规范知识库，不是固定执行流程；具体目录、入口文件、结果文件和图表目录由当前项目结构决定。

## 阶段边界

- 本阶段负责：结构验收、文本质量门禁、图表引用检查、结果一致性检查、Typst/LaTeX 编译检查、PDF 视觉检查、提交清单。
- 本阶段不负责：重新设计模型、重新跑大规模实验、重新组织整篇论文。
- 发现硬错误时，优先做不改变模型与结果的小范围修复；需要回到前序阶段时，在 `reports/VERIFY_REPORT.md` 写明负责 skill、修复任务和受影响检查，交给入口协调返工。当前仍有硬错误时为 `FAIL`；无硬错误但必需检查无法执行时为 `BLOCKED`。

## 输入

由模型先根据当前工作区判断项目布局，再把实际路径传给检查脚本。常见输入包括但不限于：

1. 论文入口文件：`main.typ`（Typst）或 `main.tex`（LaTeX）。
2. 正文章节目录或若干正文文件（`.typ` 或 `.tex`）。
3. 参考文献文件（`references.typ` 或 `references.tex`）。
4. 前序阶段的分析、建模、结果、图示报告。
5. 图表目录
6. 可复现代码目录。
7. 编译后的 PDF，或可由入口文件编译得到的输出 PDF。

不要假设论文目录一定叫 `paper/`，也不要假设结果文件一定在项目根。若项目使用不同命名，按实际结构传参并在 `reports/VERIFY_REPORT.md` 中说明。

## 按需独立复核

协作设置沿用会话或 `plan.md`，未指定时默认 `auto`。主 agent 读取 [协作协议](../1start-mathmodel/references/multi-agent.md)。完整验收中可独立分工时，按需要招募数学与数值一致性、代码复现、格式与引用审查专家；优先使用未参与被审查产物编写的新子 agent，并记录其审查范围和独立性。局部、简单的修正可保持单 agent。

先确定本轮被审查文件的版本，并明确每位专家对应下列哪些检查。审查者先在隔离状态下提交并冻结独立首稿，冻结前不得看到其他审查者结论或主 agent 的预期 PASS/FAIL；被记为独立复核者的 agent 不得参与其审查范围内生产产物的编写或修复，参与者只能记为作者自检。子 agent 只读生产产物，只将报告、复现输出或编译副本写入分配的独立目录；真实编译和复现在副本中进行，保留项目相对布局，不覆盖正式 PDF、结果或日志。多个专家不得同时运行同一套检查或修改同一份文件。未运行的检查如实标为 `NOT_RUN`，不得通过意见汇总补成 `PASS`。

主 agent 等待所需审查结果，核对关键问题的文件定位、命令和证据。满足协作协议的触发条件时执行结构化交叉质询；互补检查不为形式上的讨论而相互影响，质询后的回应作为非隔离追加意见记录，不覆盖冻结首稿。主 agent 将独立报告、质询记录和仲裁证据合并到唯一的 `reports/VERIFY_REPORT.md`。输入或生产产物发生足以影响争议命题的变化后，旧版本相关独立首稿、质询、验证任务和仲裁结论失效，应按 Step 10 对新版本重新判断并复验；已启用或明确要求独立复核时，由未参与修复的原独立审查者或新的独立 agent 复验，无法维持独立性时如实降级记录。`single` 或自动降级时如实说明未进行独立复核；若用户明确要求的独立复核无法完成，将该必需检查列为 `NOT_RUN`，按 Step 9 判为 `BLOCKED`（已有硬错误时仍为 `FAIL`）。

以下修复指令由主 agent 或其指定的前序阶段负责人执行；审查子 agent 返回发现与建议，不在审查过程中修改生产产物。

## 工作流程


### Step 1: 运行文本质量门禁

优先运行本 skill 的脚本。脚本按入口文件扩展名自动选择检查逻辑（`.typ` → Typst 检查，`.tex` → LaTeX 检查）：

```bash
set -o pipefail
mkdir -p _tmp
SCRIPT_PATH="<按当前 skill 实际位置确定>/scripts/writing_check.sh"
bash "$SCRIPT_PATH" \
  --paper-dir "$PAPER_DIR" \
  --main "$MAIN_FILE" \
  --sections-dir "$SECTIONS_DIR" \
  --references "$REFERENCES_FILE" \
  --figures-dir "$FIGURES_DIR" \
  --results-file "$RESULTS_FILE" \
  --problem-analysis "$PROBLEM_ANALYSIS_FILE" \
  --all-results "$ALL_RESULTS_FILE" \
  | tee _tmp/writing_check.log
```

如果本 skill 被复制到其他目录，使用实际脚本路径。可以先运行 `bash <script> --help` 查看参数。不要把脚本路径、论文目录或文件名写死在验收逻辑中。

脚本只扫描文本，不生成论文，也不编译 PDF。它的 `FAIL` 属于硬错误，必须修复后重跑；脚本的 `PASS` 仅代表文本门禁通过，不代表总体验收通过。脚本或运行环境不可用时，将该检查记为 `NOT_RUN`，按 Step 9 汇总结论。

### Step 2: 章节数量和标题顺序

**Typst 引擎**检查：

- 入口 `.typ` 文件中 `#include("...")` 的数量是否与实际正文结构匹配。
- include 顺序是否符合文件名前缀顺序，例如 `1_...`, `2_...`, `3_...`。
- 每个 section 是否有明确一级标题（`= 标题`，等号后有空格）。
- 标题顺序是否符合所选论文类型。

**LaTeX 引擎**检查：

- 入口 `.tex` 文件中 `\input{...}` 或 `\include{...}` 的数量是否与实际正文结构匹配。
- 章节顺序是否符合文件名前缀顺序。
- 每个 section 是否有 `\section{}` 或对应级别标题。

通用检查（两种引擎）：

- 章节文件是否缺失、重复引用、未被引用。
- 如果题目不是三问，不强行要求三段问题章节；按 `ANALYSIS_MODELING_REPORT.md` 的子问题数量核对。

### Step 3: 图表和章节匹配

**Typst 引擎**检查：

- 图表目录中的 PDF 是否在正文中被引用。
- `#figure(image(...), caption: [...])` 的图片是否真实存在。图片路径必须相对于 `.typ` 文件。
- 数据图是否放在对应结果/分析章节，非数据流程图是否放在方法/总体思路章节。

**LaTeX 引擎**检查：

- `\includegraphics{}` 引用的图片文件是否真实存在。遵循 `5writing` 的编译约定：从论文入口文件所在目录编译，主文件及通过 `\input` / `\include` 引入的章节中的显式图片路径均相对于该目录，不相对于章节目录。
- `\caption{}` 是否存在。
- 数据图是否放在对应结果/分析章节。

通用检查（两种引擎）：

- 连续图表之间是否有足够解释文字。
- caption 是否过长、过泛或与图意不一致。
- 图表编号、正文引用和章节语义是否一致。

不要生成 `*_typst_includes.typ` 或 `*_latex_includes.tex`；图表必须直接嵌在对应 section 中。

### Step 4: 写作质量和泄露检查

检查并修复：

- `TODO`、`PLACEHOLDER`、`待补充`、`待续写`、`示例数据` 等占位符。
- 论文正文出现内部工作流文件名、临时目录名、代码目录名或结果 JSON 路径。
- 过多列表式写作（Typst 中大量 `#list`、`enum`，LaTeX 中大量 `\begin{itemize}`、`\begin{enumerate}`）。
- 段落反复以"如图""由图""图 X 展示了"开头。
- 图表后没有解释、公式后没有变量含义、结论只报数不解释。

### Step 5: 数值和结果一致性

检查：

- 论文中的关键数值必须来自当前工作流声明的结果记录或结果 JSON。
- 目标函数值、误差指标、排名、权重、阈值、灵敏度结果不得与结果记录冲突。
- 如果存在汇总结果 JSON，抽取关键指标并确认论文正文中有对应结果。
- 公式中的符号应在符号说明或正文首次出现处解释。

发现数值冲突时，先核对结果来源。若可信结果记录一致而论文抄写错误，修正论文；若代码输出或结果记录本身有误，交给 `3coding-visual` 重算；若错误来自模型或假设，交给 `2analysis-modeling`。不要自行发明新结果或用改写结果文件来掩盖冲突。

### Step 6: 引用和模板规范

检查：

- 参考文献文件是否存在，或模板是否采用了其他真实参考文献机制。
- 正文引用标记（Typst 的 `@label`/`#super`，LaTeX 的 `\cite{}`）是否能对应到真实参考文献。
- 中文论文 caption、表题、摘要语言保持中文；英文论文保持英文。
- 选定的模板入口是否保留所选比赛模板的必要封面、摘要、编号、页眉页脚或提交格式。
- 不要把模板结构误删成普通空白文档。


### Step 7: 编译

复用 `5writing` 记录的项目根、入口和编译目录。执行前将 `PROJECT_ROOT`、`MAIN_FILE` 解析为实际绝对路径；Typst 的 `OUTPUT_PDF` 也使用绝对路径。先确认所选编译器可启动：工具缺失、初始化失败或访问限制使其无法运行时，记为 `NOT_RUN` 并记录原因；源码导致的编译错误记为 `FAIL`。

**Typst 编译**：

```bash
(
  cd "$(dirname "$MAIN_FILE")" || exit 1
  typst compile --root "$PROJECT_ROOT" "$(basename "$MAIN_FILE")" "$OUTPUT_PDF"
)
```

**LaTeX 编译**：

```bash
OUTPUT_PDF="${MAIN_FILE%.*}.pdf"
(
  cd "$(dirname "$MAIN_FILE")" || exit 1
  xelatex -halt-on-error -interaction=nonstopmode "$(basename "$MAIN_FILE")" &&
  xelatex -halt-on-error -interaction=nonstopmode "$(basename "$MAIN_FILE")"
)
```

LaTeX 两次编译均在入口文件所在目录执行，输出 PDF 位于同一目录。记录本次命令、退出状态、日志和输出位置；必须本次编译成功且输出 PDF 非空，不能用上次遗留的 PDF 代替成功证据。源码编译失败时修复语法、路径、图片引用或模板问题后重跑。

### Step 8: PDF 视觉检查

如果模型有视觉能力，必须把编译后的 PDF 每页导出为 PNG 并逐页查看。这个步骤用于发现纯文本扫描和编译器无法发现的版式错误。

优先使用系统已有工具导出页面 PNG；不要为了视觉检查引入沉重依赖。可选命令示例：

```bash
mkdir -p _tmp/pdf-pages
if command -v pdftoppm >/dev/null 2>&1; then
  pdftoppm -png -r 160 "$OUTPUT_PDF" _tmp/pdf-pages/page
elif command -v mutool >/dev/null 2>&1; then
  mutool draw -r 160 -o _tmp/pdf-pages/page-%03d.png "$OUTPUT_PDF"
elif command -v magick >/dev/null 2>&1; then
  magick -density 160 "$OUTPUT_PDF" _tmp/pdf-pages/page-%03d.png
else
  echo "No PDF rasterizer found; record visual check as not run."
fi
```

导出后逐页检查：

- 页面是否空白、缺页、页数异常或页面尺寸异常。
- 标题、摘要、正文、页眉页脚、页码是否被裁切或位置明显错误。
- 表格是否超出页边距，单元格文字是否重叠、溢出、被截断。
- 图片、图题、表题、公式、编号是否与正文重叠。
- 公式是否越界，长公式是否压到页边距或下一段文字。
- 列表、段落、脚注、参考文献是否出现异常大空白、重叠或孤立残行。
- 中文/英文/数学符号字体是否明显缺字、乱码或 fallback 异常。
- 封面、摘要页、目录、附录等模板关键页面是否保留比赛要求的视觉结构。

如果是模板转换或已有参考 PDF 的项目，还应将不同引擎的 PDF 都逐页导出 PNG，按页对比版式差异；页数或页面尺寸不一致必须记录为硬错误或明确说明原因。

如果模型没有视觉能力，或所有可用页面导出工具均无法完成导出，在 `reports/VERIFY_REPORT.md` 将视觉检查记为 `NOT_RUN` 并说明原因；仍完成可执行的 PDF 非空、页数、页面尺寸等基础检查。基础检查不能替代逐页视觉检查，也不能据此将总体结论写为 `PASS`。

### Step 9: 写验收报告

创建 `reports/VERIFY_REPORT.md`：

```markdown
# 验证和验收报告

## 结论
PASS / FAIL / BLOCKED

提交就绪：是 / 否（仅总体结论为 PASS 时为“是”）

## 协作与独立性
实际模式、审查者与负责范围、输入版本、报告位置、未完成任务及降级原因；如触发交叉质询，记录争议编号、质询与回应、立场变化、判别检查和仲裁证据。

## 检查项
| 检查项 | 结果（PASS / FAIL / WARN / NOT_RUN） | 证据或未执行原因 |
| --- | --- | --- |

## 章节结构

## 图表引用

## 数值一致性

## 文本质量门禁

## 编译

## PDF 视觉检查

## 仍需处理的问题

## 返工任务
| 问题及证据 | 负责 skill | 修复任务或缺少条件 | 受影响产物与复验项 | 状态 |
| --- | --- | --- | --- | --- |

## 修复与复验记录
```

总体结论按以下顺序判定：

1. 当前产物仍有硬错误，结论为 `FAIL`；即使同时有未执行检查，也不能把已知错误改记为 `BLOCKED`。
2. 没有已知硬错误，但文本门禁、关键数值一致性、编译或逐页视觉检查等必需检查因缺工具、初始化失败、访问受限、缺少必要输入而未完成，结论为 `BLOCKED`，并列明 `NOT_RUN` 项和恢复条件。
3. 必需检查均已实际通过、硬错误均已修复、核心图表已引用、数值一致、本次编译成功且 PDF 非空、逐页视觉检查通过，才写 `PASS`。非阻断的 `WARN` 可保留，但需写明影响。

`FAIL` 和 `BLOCKED` 均表示尚未提交就绪。说明不可编译或无法视觉检查的原因，只完成了阻塞记录，不能替代相应检查。

### Step 10: 返工交接与复验

需要前序阶段处理时，按问题根因填写“返工任务”：

| 根因 | 负责 skill | 复验重点 |
| --- | --- | --- |
| 题意、假设、变量或模型公式错误 | `2analysis-modeling` | 修正模型后检查计算、相关图示和论文是否同步 |
| 数据处理、代码、约束校验或结果记录错误 | `3coding-visual` | 重算受影响结果与数据图，再检查论文数值一致性 |
| 非数据流程图或架构图内容、导出错误 | `4drawio` | 源图、导出文件及论文引用一致性 |
| 可信结果抄写错误、章节、路径、引文或排版错误 | `5writing` | 文本、图片引用、编译与受影响页面 |

`6verity` 可直接修复明确的小范围写作错误；需要重建模型、重算结果或重写主要内容时，交给对应 skill，完整工作流由 `1start-mathmodel` 继续协调，单独调用验收时也要明确列出交接任务。工具或输入阻塞应记录缺少的条件，不应要求修改正确的模型或数值。

修复后复验原失败项及受修改影响的检查；仅可复用对应产物未变化的通过证据。保留问题、修复内容和复验结果，使总体结论对应当前产物，不沿用旧的 `PASS`。

## 硬错误标准

以下问题必须判定 `FAIL`：

- 缺少选定的论文入口文件（`main.typ` 或 `main.tex`）或核心正文。
- 论文入口引用的章节文件不存在。
- Typst 入口缺少 `#include`；LaTeX 入口缺少 `\input`/`\include`。
- 正文章节缺少一级标题（Typst `= ` 后缺空格，LaTeX `\section{}` 缺失）。
- 章节顺序明显错误或重复。
- 正文仍有占位符。
- 正文泄露内部工作流文件名。
- 引用的图片不存在。
- 关键数值与结果记录冲突。
- 编译器可用但论文编译失败。
- 编译后的 PDF 为空、缺页、页数异常或页面尺寸异常且无法解释。
- 视觉检查发现正文、表格、图片、公式、页眉页脚、页码等关键元素重叠、裁切、越界或乱码。

## 警告标准

以下问题可判定为 `WARN`，但应尽量修复：

- 未引用的备用图片。
- 某章节过短或明显不均衡。
- caption 偏长。
- 参考文献偏少。
- 图表后解释文字不足。
- 代码完整复现耗时过长，只做了轻量检查。
