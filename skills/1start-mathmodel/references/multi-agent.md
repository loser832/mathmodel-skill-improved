# 数学建模多 agent 协作协议

本文件由 `1start-mathmodel`、`2analysis-modeling` 和 `6verity` 按需读取。它只负责阶段内分工，现有阶段产物与验收规则继续生效。

## 启用与分工

- 用户最新明确指示优先，其次为 `plan.md` 的协作设置；缺省 `auto`，最大同时 3 个子 agent。始终按宿主真实可用并发下调，人数由互补任务决定，不为凑人数创建角色。
- `single` 不创建子 agent。`auto` 在建模阶段有重要假设、候选模型分歧、独立数据检查，或完整验收有不同审查范围可分工时委派。简单修改、只有单一紧耦合步骤时由主 agent 完成。
- `multi` 在建模和验收阶段执行真实委派；若无法建立独立任务或工具不可用，先记录原因并完成可执行部分，不伪造多 agent 执行。
- 只有主 agent 招募、分配、等待和汇总。作为已委派子 agent 读取本文件时，只处理任务包，不再招募、不重新运行整个 skill。遇到职责外问题返回主 agent。
- `3coding-visual`、`4drawio`、`5writing` 由明确负责人顺序执行；这一版的多 agent 不跨越阶段依赖。

## 动态角色

按任务选择互补职责，角色可以复用或合并，但同一产物的作者不得被记为独立审查者。

| 阶段与角色 | 负责内容 | 返回证据 |
| --- | --- | --- |
| 建模：数据与题意审查 | 单位、变量可用性、缺失、歧义、训练验证隔离、约束来源 | 题面或字段定位、可用与不可用输入、影响模型的未知信息 |
| 建模：模型方案 | 按题型提出公式、目标、约束、求解与校验路径 | 明确假设、可实现模型、适用条件与局限 |
| 建模：备选方案或反例检查 | 提出有实质差异的方案，或检查模型边界、不可行情形与假设敏感性 | 方案差异、反例、小规模验算与需要进一步验证的指标 |
| 验收：数学与数值一致性 | 题目覆盖、模型公式、约束、结果与论文关键数值对应关系 | 具体文件位置、计算核对与冲突清单 |
| 验收：代码复现 | 运行条件、核心实现与报告一致性、结果可复现性 | 实际命令、退出状态、输出对照、未执行原因 |
| 验收：格式与引用 | 文本门禁、章节、图片、引文、编译和逐页视觉检查 | 文件或页面位置、脚本与编译日志、真实视觉检查结果 |

建模方案先独立分析同一份原始材料，再交换与具体分歧有关的证据。独立审查优先使用新子 agent，仅提供原始任务、待审产物和检查要求，不告知预期 PASS/FAIL，也不把其他审查者结论当作已证实事实。

## 委派任务包

每次真实委派前明确以下信息，可用简洁文本，不强制 JSON：

- 任务编号、所属阶段、角色和要回答的具体问题。
- 输入文件绝对路径及本轮版本标识（如内容哈希或固定副本），共同的题面事实、单位、约束和评价口径。
- 依赖关系与所需完成条件；等待前序结论的工作不提前执行。
- 允许的操作、允许写入的确切目录、不能改动的共享产物。
- 输出报告位置，以及结论所需的文件定位、运行记录或推导依据。
- 本任务适用的时间、计算预算与中止条件；没有授权或无法执行的动作返回原因，不自行扩大任务。

主 agent 记录宿主返回的真实子 agent 标识与任务的对应关系。只采用宿主实际存在的创建、发送任务、等待、读取结果工具；不要假设 `Agent` 或某个函数名在所有环境中都存在。只有角色提示词、串行自问自答、没有真实创建成功的调用，不算独立 agent 执行。

## 产物与写入归属

- 原始题面、原始数据和本轮已确定的上游产物供所有专家只读。主 agent 为每位专家分配独立的 `reports/agents/<阶段>/<轮次>/<任务>/` 目录，报告及临时验算文件均写入该目录。
- `plan.md`、`todo.md`、`reports/ANALYSIS_MODELING_REPORT.md` 和 `reports/VERIFY_REPORT.md` 由主 agent 唯一写入。子 agent 返回报告或修改建议；主 agent 审核后整合。生产代码、结果、图表、论文仍由各阶段负责人维护。
- 审查子 agent 如需编译或复现，使用任务目录中的项目副本，保留原始相对布局，明确来源版本；不覆盖正式结果或 PDF。超出任务包的写入、依赖安装或环境修改交回主 agent，原有权限边界不变。
- 主 agent 在同一轮审查期间不修改正在被审查的文件。必须修改时，通知相关专家停止或重取输入，将旧版本相关结果标为过期，再复验。

## 返回格式

每位专家返回可检查的摘要，并在已分配目录保存完整报告：

```text
任务编号 / 角色 / 输入版本：
任务状态：完成 / 部分完成 / 阻塞 / 失败
结论与适用范围：
证据：文件位置、关键推导、实际命令与输出
发现的问题或备选方案：
不确定性、未执行项及原因：
产物绝对路径：
需要主 agent 处理的事项：
```

任务“完成”只表示分配的工作完成，不等同于论文验收 PASS。未实际运行的实验、编译、视觉检查均应说明；专家置信表达不能代替证据。

## 结构化交叉质询

交叉质询用于暴露决策关键前提并形成可执行的判别检查，不用于追求表面共识，也不是每次多 agent 委派的固定环节。

1. **先独立后质询**：相关专家先在隔离状态下提交并冻结独立首稿，记录输入版本；冻结前不得向其展示其他专家的结论、主 agent 的倾向或预期 PASS/FAIL。针对性审查必需的既有方案或产物可作为明确的待检验对象提供，但不得附带预期结论。质询后的回应作为非隔离追加意见单独记录，不回写首稿；回应本身不得称为独立发现，但不抹去冻结首稿原有的独立性。
2. **触发条件**：主 agent 核对现有题面、数据和产物后，关键假设、模型选择、约束可行性、评价口径、关键数值或验收结论仍存在实质冲突，且定向回应或判别检查可能影响决策时必须触发。明确证据已直接解决的分歧只记录仲裁，不再质询。每轮可额外抽查至多 1 个表面一致但依据包含互不相容关键前提或遗漏高影响失败边界的结论；单份报告仅因未按任务包提供必要证据时，先退回补全，不单独触发质询。互补分工、措辞差异和不影响决策的局部差异不触发。
3. **争议选择**：主 agent 先区分互补观点与真正冲突，再选取至多 3 个会改变模型选择、结果可信度或验收状态的命题；上述一致结论抽查包含在此上限内。每个命题指定一名质询方和一名被质询方，每方只在自身任务范围和证据能力内发言。
4. **定向质询**：由主 agent 转交质询包，不启动无边界的自由群聊。质询方必须给出争议编号、被质询命题、同意/部分同意/反对的立场、题面或文件定位、反例或失败边界、建议的可证伪检查，以及什么结果会改变自己的判断。一个命题只包含一个定向质询及其回应；回应不得自行扩展成反向质询，确有另一独立命题时另设争议编号并计入总上限。
5. **强制回应**：被质询方必须逐项回答，并明确选择“维持 / 修正 / 撤回”原结论，给出依据、更新后的适用条件和仍未解决的问题。回避核心命题、只重复原结论或只诉诸置信度不算有效回应。
6. **实验优先与停止条件**：每个争议默认一次质询和一次回应。能够通过数学证明、边界验算、敏感性分析、消融、对照实验或代码复现低成本判别时，优先追加一个有完成条件的验证任务，而不是延长辩论。只有出现会改变判断的新证据时才可追加一轮；无新增证据、达到任务预算或结果仍不可判别时停止，保留条件分支与不确定性。
7. **证据仲裁**：主 agent 按可追溯题面、数据质量、数学证明、约束验证和可复现实验裁决，不按票数、措辞强弱或“说服成功”裁决。质询记录进入阶段报告或协作记录，不写入最终竞赛论文。
8. **验收独立性**：`6verity` 的审查者在独立首稿冻结前保持隔离，质询只用于澄清同一检查上的冲突，不能把 `NOT_RUN` 补成 `PASS`。在已启用独立复核或用户明确要求独立复核的验收轮次中，生产产物修复后，相关复验由未参与修复的原独立审查者或新的独立 agent 执行；参与修复者不得审查自己的修改。`single` 或自动降级时按 `6verity` 记录实际复验方式，不得声称完成了独立复核。
9. **版本失效**：输入版本或被审生产产物发生足以影响争议命题的变化时，相关独立首稿、质询与回应、验证任务和仲裁结论均标记为过期。主 agent 对新版本重新判断触发条件并执行受影响的复验，不沿用旧结论。

## 汇总、分歧与复验

1. 主 agent 等待所有必要任务返回，核对原题覆盖、职责是否重复、输入版本、证据与输出文件。边等待边做不冲突的整合准备，避免重复执行已委派任务。
2. 比较模型时使用相同数据口径、约束和指标。先区分互补结论与真正冲突；满足触发条件时执行结构化交叉质询，再把仍可判别的分歧转为边界验算、敏感性分析或对照实验任务，写明什么结果会改变选择。
3. 优先采用可追溯题面、数学证明、实际约束验证和可复现实验结果。多数票和专家人数不决定结论；证据不足时保留不确定性，不把多个同模型角色的一致表态当成独立证实。
4. 默认完成一轮独立分析与合并；交叉质询遵守一次往返和证据增量停止条件，只有具体未决问题需要新证据时才追加针对性任务。没有新增证据来源或预算不足时结束讨论，记录未决项与下一步，不机械执行固定轮数辩论。
5. 建模结论整合到分析报告，最终数值仍交给代码阶段。验收结论按 `6verity` 的 FAIL 优先、必需检查未执行则 BLOCKED、实际通过才 PASS 的规则汇总，不平均专家投票。
6. 修复生产产物交给原阶段负责人；主 agent 更新计划、待办与受影响检查，只复用对应产物未变化的既有证据。

## 超时、失败与能力降级

- 并发名额不足时使用更小批次或顺序启动真实子 agent，尊重宿主上限；不能靠递归招募绕过限制。
- 子 agent 失败或超时，先检查已留下的产物，记录失败与覆盖缺口。可更换 agent 或由主 agent 接管剩余工作；接管后只能标为主 agent 检查，不能标为独立复核。
- `auto` 下工具不可用时退回单 agent，记录实际模式及原因，继续原有检查；这本身不把其余已完成工作判失败。
- 用户明确要求 `multi` 或独立复核，而真实委派/独立检查未完成时，明确记录该要求尚未满足。验收中将所需独立复核列为 `NOT_RUN`，总体按 `6verity` 规则处理；建模中记录部分完成及待补审查，不声称已完成要求。
- 模式、人员、输入版本、输出位置、分歧处理与降级原因进入现有计划或阶段报告；不把协作过程和内部路径写入最终竞赛论文。
